# Process Monitor для Active Directory

Графическое приложение на PowerShell 5.1: собирает запущенные процессы со всех компьютеров домена
(Windows Server 2008 / 2012 и клиенты), показывает их в таблице `№ | Время запуска процесса | Имя | Хэш`
(дополнительно — компьютер, пользователь, запустивший процесс, и путь; дата самого сканирования хранится отдельно и выбирается в поле «Сканирование») и позволяет заблокировать запуск файла по его хэшу.

**Блокировка не использует групповую политику (GPO/SRP).** Список заблокированных хэшей хранится только в
данных самого приложения и применяется мониторингом: после каждого сканирования (ручного или планового)
свежесобранные процессы сверяются с этим списком, и совпавшие сразу закрываются. Дополнительно, для каждой
блокировки отдельно, можно включить полную блокировку учётной записи домена у того, кого поймают с этим
файлом — см. «Как работает блокировка» ниже.

## Как это работает

| Задача | Реализация |
|---|---|
| Список компьютеров | LDAP-запрос через ADSI (модуль ActiveDirectory не нужен), только включённые компьютеры с Windows; можно ограничить OU |
| Проверка «включён ли компьютер» | перед сбором каждый компьютер проверяется пингом (ICMP, параллельно, ~1 с на все сразу) — выключенные/недоступные по сети сразу считаются сбоем с понятной причиной, вместо того чтобы ждать таймаута WinRM на каждый |
| Сбор процессов | `Invoke-Command` (WinRM) параллельно, на цели `Get-WmiObject Win32_Process`; на целях достаточно PowerShell 2.0 |
| Хэши | MD5, SHA1 и SHA256 считаются на самом компьютере за один проход по файлу; в таблице выбирается нужный алгоритм |
| Пользователь | Владелец каждого процесса (кто его запустил) — метод WMI `GetOwner()`, в виде `ДОМЕН\логин`; системные процессы показываются как `NT AUTHORITY\SYSTEM` и т. п., если владельца определить нельзя — пусто. Один и тот же файл, запущенный разными пользователями, показывается отдельными строками |
| Время запуска | Когда процесс был запущен (`Win32_Process.CreationDate`) — в часовом поясе того компьютера, где он работает; если WMI не отдал время, поле пустое |
| Хранение | JSON-файлы в папке `data\`: каждое сканирование сохраняется отдельным файлом с датой, история не стирается |
| Блокировка по хэшу | хэш добавляется в собственный список приложения (никакой GPO); можно выбрать сразу несколько строк (Ctrl/Shift+клик) и заблокировать все разом |
| Мониторинг и enforcement | после каждого сканирования (ручного или планового) свежесобранные процессы сверяются с активными блокировками, и совпавшие сразу закрываются с уведомлением пользователю — см. «Как работает блокировка» ниже |
| Блокировка учётной записи (опционально) | для каждой блокировки отдельно можно включить: при обнаружении — завершение сеанса и ПОЛНОЕ отключение учётной записи пользователя в домене — см. «Как работает блокировка» |

## Требования

На компьютере администратора (откуда запускается приложение):

* Windows PowerShell 5.1, права локального администратора на целевых компьютерах (для завершения процессов и
  сеансов через WMI) и права на изменение атрибута `userAccountControl` учётных записей в AD (для блокировки
  учётной записи — обычно это право делегировано службе безопасности/helpdesk, либо используется учётная
  запись администратора домена);
* модуль **GroupPolicy больше не требуется** — приложение не использует групповую политику вообще.

Сторонние драйверы и модули для хранения данных не нужны.

На целевых компьютерах:

* включён WinRM / PowerShell Remoting (`Enable-PSRemoting`, либо GPO «Allow remote server management through WinRM»);
* открыт порт 5985/TCP для администратора.

Если какой-то компьютер попадает в журнал с ошибкой подключения («нет данных: Сбой подключения к удаленному
серверу...», «WinRM не удаётся выполнить операцию...» и т. п.) — на нём не настроен или заблокирован
брандмауэром WinRM. Запустите на ЭТОМ компьютере (под администратором) прилагаемый `Setup-WinRM-Target.ps1` —
он включает PowerShell Remoting и явно открывает WinRM в брандмауэре для всех сетевых профилей (в т. ч. когда
сетевой профиль компьютера определился как «Общедоступная сеть», а не «Сеть домена» — самая частая причина
ошибки «WinRM не удаётся выполнить операцию»/«ограничивает доступ... в той же локальной подсети», так как
компьютер администратора обычно в другой подсети). Подробности и способы запуска без уже работающего WinRM
(GPO startup script, PsExec) — в комментариях самого файла.

Чтобы эта настройка применялась **автоматически на всех компьютерах домена** (сценарий запуска компьютера
через GPO, от имени SYSTEM, без необходимости заходить на каждый компьютер вручную) — см.
**[Deploy-WinRM-GPO.md](Deploy-WinRM-GPO.md)**.

## Запуск

```powershell
powershell -STA -ExecutionPolicy Bypass -File .\ProcessMonitor.ps1
```

1. Вкладка **Компьютеры** → «Загрузить из AD» (при желании укажите DN подразделения), отметьте нужные → «Собрать процессы».
   Кнопка «Сохранить список для плановых сканирований» запоминает отмеченные компьютеры для запуска без окна
   (см. раздел «Плановые сканирования» ниже).
2. Вкладка **Процессы**: выбор сканирования, алгоритма хэша, поиск по имени/хэшу/компьютеру/пути.
   Номер строки в колонке `№` пересчитывается при сортировке и поиске.
3. При необходимости отметьте на вкладке **Блокировки** галочку «Также блокировать учётную запись пользователя
   при обнаружении» — она решает, что будет происходить при обнаружении запущенным именно для блокировок,
   которые вы создадите ДАЛЬШЕ (на уже существующие блокировки не влияет).
4. На вкладке **Процессы** выберите строку → **«Заблокировать по хэшу…»**. Можно выделить несколько строк
   (Ctrl/Shift+клик) и заблокировать их все одним нажатием — одно общее подтверждение на весь список, один и
   тот же файл на разных компьютерах считается одной блокировкой, а не несколькими.
5. Вкладка **Блокировки**: список всех блокировок (активных и снятых), сколько раз и когда в последний раз
   сканирование заставало заблокированный файл запущенным, «Снять блокировку».
6. Вкладка **Пользователи**: «Загрузить из AD» — все пользователи домена деревом по подразделениям (OU),
   строка подсвечена зелёным (учётная запись активна) или красным (отключена) — удобно проверить результат
   «Блокировки учётной записи» (см. ниже) без необходимости открывать ADUC; обновляется автоматически сразу
   после того, как приложение кого-то заблокирует. Правый клик по пользователю → «Включить учётную запись
   обратно» — снимает блокировку без переключения в ADUC/dsa.msc. Снизу — журнал блокировок учётных записей
   (кто, когда, за каким компьютером и за какой файл), та же выписка, что в `data\logs\account-blocks.log`.
7. Вкладка **Журнал**: компьютеры, которые не ответили, и причина; результаты применения блокировок.

Данные собираются под учётной записью, от имени которой запущено приложение.

## Плановые сканирования

Чтобы данные обновлялись сами, без открытого окна:

1. На вкладке **Компьютеры** отметьте нужные компьютеры и нажмите **«Сохранить список для плановых сканирований»**
   (список сохраняется отдельно от обычных галочек, в `data\scheduled-computers.json`; кнопка «Загрузить
   сохранённый список» показывает его снова, если нужно свериться или поправить).
2. Добавьте в **Планировщик заданий Windows** (`taskschd.msc`) задание, запускающее:
   ```
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\путь\ProcessMonitor.ps1" -ScheduledScan
   ```
   Окно при этом не открывается; результат — обычное новое сканирование (видно на вкладке «Процессы» при
   следующем запуске окна) и запись в ОТДЕЛЬНЫЙ файл `data\logs\scheduled-scan.log` (не в основной
   `processmonitor.log` — см. «Журнал работы» ниже).

**Важно про учётную запись задания.** WinRM к ДРУГИМ компьютерам нужна сетевая идентичность с правами на них.
Задание, запущенное как `SYSTEM` (частый вариант по умолчанию), сетевого доступа к другим машинам не имеет и
скорее всего не сможет их опросить. Создавайте задание от настоящей учётной записи (доменной, с правами на
WinRM/WMI целевых компьютеров, и с правами на изменение `userAccountControl` в AD, если используете блокировку
учётных записей) с опцией **«Run whether user is logged on or not»** и сохранённым паролем — так, как обычно
настраивают сервисные задания в Планировщике.

`-ScheduledScan` сам новых блокировок не создаёт — решение заблокировать что-либо по-прежнему принимает человек
на вкладке «Процессы»; это сделано намеренно: скрипт по расписанию не должен сам решать, что запрещать в домене.
Но УЖЕ существующие активные блокировки он проверяет и применяет автоматически — это ЕДИНСТВЕННЫЙ механизм,
которым блокировка вообще работает (см. «Как работает блокировка» ниже): после каждого планового сканирования
запущенные экземпляры уже заблокированных файлов сразу закрываются. Поэтому частота плановых сканирований —
это и есть то, насколько быстро такой процесс будет обнаружен и закрыт после повторного запуска.

**«Постоянное» сканирование активных компьютеров.** Само приложение не содержит бесконечного цикла — это
сознательно оставлено Планировщику заданий: поставьте в задании повторение (вкладка «Триггеры» → «Повторять
задачу каждые: ...», например каждые 5 минут) и `-ScheduledScan` будет запускаться постоянно, снова и снова,
без участия человека. Каждый такой запуск сам проверяет пингом, какие из сохранённого списка компьютеров сейчас
включены (см. таблицу выше) — выключенные просто пропускаются в этот раз (с пометкой в журнале, не как ошибка)
и будут опрошены при следующем запуске, когда включатся. Отдельно настраивать список «активных» компьютеров не
нужно — он определяется заново при каждом запуске.

## Журнал работы

Всё, что видно на вкладке «Журнал» (ошибки, не ответившие компьютеры, итоги сбора и блокировок), одновременно дописывается
в файл `data\logs\processmonitor.log` с датой и временем каждой записи. При перезапуске файл не затирается, а в окне
показываются последние 200 строк прошлых запусков. Кнопка «Открыть файл журнала» открывает файл в Блокноте. Когда файл
вырастает больше 5 МБ, он переименовывается в `processmonitor.log.1` (предыдущая копия `.1` заменяется) и начинается новый.
Ошибка записи в журнал (нет прав, файл занят) программу не останавливает.

**Отдельный журнал блокировок учётных записей.** Все события блокировки учётной записи (кого, когда и за какой
файл заблокировали, а также неудачные попытки — например, нет прав или учётная запись не найдена) дополнительно
записываются в отдельный файл `data\logs\account-blocks.log` — выписка специально для аудита этой, самой
серьёзной меры, с той же ротацией при превышении 5 МБ.

**Отдельный журнал плановых сканирований.** Всё, что происходит при запуске по расписанию (`-ScheduledScan`,
см. «Плановые сканирования» выше) — старт/итог сбора, компьютеры без ответа, срабатывания уже существующих
блокировок — пишется в СВОЙ файл `data\logs\scheduled-scan.log`, а не в основной `processmonitor.log`: так
видно отдельно, что происходило именно в фоновых запусках планировщика (когда никто не смотрел в окно), не
перемешанное с записями от ручных запусков через интерфейс. Та же ротация при превышении 5 МБ.

## Самопроверка

Перед первым боевым запуском выполните на своей машине:

```powershell
powershell -STA -ExecutionPolicy Bypass -File .\ProcessMonitor.ps1 -SelfTest
```

Окно не открывается; скрипт проверяет версию PowerShell, JSON-хранилище (во временной папке), хэширование процессов
(с эталоном `Get-FileHash`), Windows Forms, а также доступ к AD и работу WinRM на этом компьютере.
Каждый пункт печатается как `[ OK ]`, `[WARN]` (необязательно: нет AD или WinRM) или `[FAIL]`.

## Как работает блокировка

Блокировка по хэшу — это запись в собственном списке приложения (`data\blocks.json`), а не правило в GPO. Сама по
себе такая запись ничего не блокирует «превентивно» — enforcement даёт только мониторинг:

* **После КАЖДОГО сканирования** (и ручного, кнопка «Собрать процессы», и планового, `-ScheduledScan` — см.
  «Плановые сканирования») приложение сверяет свежесобранные процессы со списком активных блокировок.
* Если хэш совпал — на всех компьютерах, где файл найден запущенным, он **сразу закрывается**
  (`Win32_Process.Terminate()`), а пользователю показывается уведомление на экране (`msg.exe`) — по умолчанию
  «Нельзя такое запускать: «‹имя файла›» заблокировано политикой безопасности.» (текст можно поменять в коде
  через `$script:NotifyTemplate`).
* Это же происходит сразу при самой блокировке — если файл уже был запущен на момент создания блокировки
  (приложение сверяется с последним сканированием), закрытие происходит немедленно, не дожидаясь следующего
  прохода.
* **Это не мгновенная, превентивная блокировка** (как была бы у SRP) — между запуском заблокированного файла и
  ближайшим сканированием есть окно. Насколько оно короткое, зависит от частоты плановых сканирований.
* Журнал показывает результат по каждому компьютеру: сколько запущенных экземпляров **найдено**, сколько
  реально **завершено** и скольким пользователям показано уведомление. Found = 0 при непустом списке
  компьютеров значит, что на момент применения процесс уже не был запущен. Found > Killed значит, что
  экземпляры найдены, но `Terminate()` их не завершил; причина указывается рядом («нет прав на завершение
  процесса» — самая частая: учётная запись, под которой запущено приложение, должна быть локальным
  администратором на целевом компьютере).
* Блокировать файлы в `X:\Windows\…` запрещено программно: правило на `svchost.exe`, `explorer.exe` и т. п.
  остановило бы весь домен.
* Снятие блокировки (кнопка «Снять блокировку») — это просто отметка «снята» в списке; дальнейшие сканирования
  перестают реагировать на этот хэш. Можно выделить несколько блокировок (Ctrl/Shift+клик, например, после
  фильтра по группе) и снять их все одним нажатием — уже снятые среди выделенных просто пропускаются.

### Группы/категории блокировок

Поле **«Группа»** на вкладке «Блокировки» — свободный текст (например, «Игры», «Мессенджеры», «Торренты» —
любое своё название), который читается один раз в момент создания КОНКРЕТНОЙ блокировки и сохраняется вместе
с ней; на уже существующие блокировки изменение поля не влияет. Никакого отдельного смысла для приложения
не несёт — только для вашего удобства: **«Фильтр по группе»** рядом — выпадающий список с уже встречавшимися
значениями (обновляется сам при каждом обновлении таблицы) плюс можно ввести любой текст — фильтрует таблицу
по подстроке (регистр не важен), например «игр» найдёт и «Игры», и «Игры (Steam)». Удобно, когда блокировок
становится много: отфильтровать по категории и снять все разом.

### Журнал обнаружений (кто и сколько раз повторно запускал заблокированный файл)

На вкладке «Блокировки» для каждой блокировки видно не только суммарное число обнаружений (**«Срабатываний»**),
но и когда, на каком компьютере и под каким пользователем файл был обнаружен запущенным **в последний раз**
(колонки «Последнее обнаружение», «Последний компьютер», «Последний пользователь»).

Чтобы увидеть **каждый отдельный случай** (а не только последний), выберите блокировку и нажмите **«История
обнаружений»** — откроется окно со списком всех обнаружений этой блокировки: время, компьютер, пользователь,
путь к файлу. Это позволяет увидеть, например, что один и тот же человек запускал заблокированное ПО повторно
несколько раз подряд, или что его запускали разные люди на разных компьютерах. Данные сохраняются в
`data\block-hits.json` и не теряются при перезапуске программы.

### Блокировка учётной записи (опционально, на каждую блокировку отдельно)

На вкладке «Блокировки» есть галочка **«Также блокировать учётную запись пользователя при обнаружении»**. Она
читается в момент создания КОНКРЕТНОЙ блокировки (кнопка «Заблокировать по хэшу…») и сохраняется вместе с этой
блокировкой — на уже существующие блокировки изменение галочки не влияет; чтобы поменять решение, нужно снять
блокировку и создать заново.

Если включено, то при обнаружении этого файла запущенным (сейчас и при каждом следующем сканировании) происходит,
в таком порядке:

1. Пользователю показывается **другое** уведомление — не обычное, а объясняющее, что учётная запись будет
   заблокирована и для разблокировки нужно обратиться к системному администратору (`$script:LockNotifyTemplate`).
2. Процесс закрывается (`Win32_Process.Terminate()`).
3. Сеанс пользователя **принудительно завершается** (`logoff.exe`) — здесь это происходит ВСЕГДА, отдельного
   вопроса администратору (как для обычной блокировки) не задаётся: оставлять пользователя в уже открытом
   сеансе при отключении его учётной записи бессмысленно.
4. Учётная запись пользователя в AD **полностью отключается** (бит `ACCOUNTDISABLE` в атрибуте
   `userAccountControl`, через ADSI — без модуля ActiveDirectory) — человек не сможет войти вообще никуда в
   домене (ни на один компьютер, почту и т. п.), пока администратор не включит учётную запись обратно вручную.
5. Событие записывается в отдельный журнал блокировок учётных записей (`data\logs\account-blocks.log`) — кто,
   когда, за какой файл и с каким результатом (успех или причина неудачи).

**Важная техническая деталь: отключение учётной записи выполняется с машины АДМИНИСТРАТОРА, а не с того
компьютера, где поймали процесс.** Шаги 1–3 выполняются удалённо (через WinRM, как и всё остальное применение),
а шаг 4 (запись в AD) — локально на машине, где запущено приложение (или где выполняется плановое
сканирование), уже после того как удалённая часть отработает и вернёт результат. Причина — «двойной переход»
(double hop) Kerberos: если бы запись в AD пыталась выполниться НА удалённом компьютере внутри сеанса
`Invoke-Command`, у неё, скорее всего, не было бы прав — PowerShell Remoting по умолчанию не передаёт учётные
данные администратора дальше, на третью систему (контроллер домена), поэтому компьютер обращался бы к AD от
своего ИМЕНИ и, вероятнее всего, получил бы отказ в доступе.

**Это не проверено на реальном домене** (как и доступ к AD в целом в этом приложении) — перед использованием на
живых пользователях обязательно опробуйте на тестовой учётной записи и тестовом файле: заблокируйте что-нибудь
безобидное с включённой галочкой, запустите на тестовом компьютере под тестовой учётной записью, дождитесь
планового сканирования (или запустите сбор вручную) и убедитесь, что: сеанс действительно завершился, учётная
запись действительно отключилась (`Get-ADUser <sam> -Properties Enabled` или через `dsa.msc`), и в
`account-blocks.log` появилась соответствующая строка.

### Ограничения, о которых нужно знать

* **Не проверено на живом домене.** Код проверен только на синтаксис и отдельные части (хэширование, JSON-хранилище,
  разбор заданий); интерфейс, WinRM, отключение учётной записи в AD нужно сначала опробовать на тестовой машине
  и тестовой учётной записи.
* **Между запуском заблокированного файла и его обнаружением есть окно** — ровно по длине интервала плановых
  сканирований (см. «Плановые сканирования»). Это не мгновенная, превентивная блокировка.
* Один файл — один хэш: перекомпилированная или изменённая копия имеет другой хэш и правилом не блокируется.
* Процессы без доступного пути к файлу (System, Idle) пропускаются; файлы, которые не удалось прочитать, тоже.
* Блокировка учётной записи отключает ВЕСЬ доступ человека в домене, а не только к заблокированному файлу —
  это намеренно серьёзная мера (см. выше), включайте галочку обдуманно.

## Структура и хранение данных

Всё приложение — один файл `ProcessMonitor.ps1` (интерфейс, хранилище, сбор, блокировка). Данные лежат в папке `data\`
рядом со скриптом (другая папка — параметр `-DataPath`):

```
data\scans.json                список сканирований: номер, дата, сколько компьютеров ответило, их имена
data\scans\scan-000001.json    процессы одного сканирования (отдельный файл на каждое)
data\blocks.json               журнал блокировок (хэш, LockAccount, сколько раз обнаружен, когда/где/кто в последний раз)
data\block-hits.json           подробный журнал обнаружений: каждый отдельный случай (время, компьютер, пользователь,
                                путь) - см. "Журнал обнаружений" и кнопку "История обнаружений" на вкладке "Блокировки"
data\scheduled-computers.json  список компьютеров для плановых сканирований (см. "Плановые сканирования")
data\logs\processmonitor.log   журнал работы программы - ручные запуски через интерфейс (записи дописываются, не стираются)
data\logs\scheduled-scan.log   отдельный журнал ПЛАНОВЫХ сканирований (-ScheduledScan, запуск по расписанию без окна)
data\logs\scheduled-processes.log  построчный список КАЖДОГО процесса, найденного плановым сканированием
                                (компьютер, пользователь, имя, путь, когда запущен) - обычный текст, можно
                                просмотреть без запуска приложения
data\logs\account-blocks.log   отдельный журнал блокировок учётных записей (см. "Блокировка учётной записи")
```

Файлы — обычный UTF-8 JSON, их можно открыть любым редактором. Запись идёт через временный файл, поэтому обрыв
не портит уже сохранённое. Приложение рассчитано на один запущенный экземпляр. Данные, ранее сохранённые в SQLite
(`processes.db`) или в старых версиях с GPO (GpoName/RuleId/Scope/Target), не импортируются — поля, которых
больше нет в схеме, при чтении старых файлов просто игнорируются.

Файл сохранён в UTF-8 **с BOM** — это нужно Windows PowerShell 5.1 для корректного чтения кириллицы.
Если будете править, сохраняйте в той же кодировке (иначе кириллица будет испорчена).
