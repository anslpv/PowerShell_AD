# Process Monitor для Active Directory

Графическое приложение на PowerShell 5.1: собирает запущенные процессы со всех компьютеров домена
(Windows Server 2008 / 2012 и клиенты), показывает их в таблице `№ | Время запуска процесса | Имя | Хэш`
(дополнительно — компьютер, пользователь, запустивший процесс, и путь; дата самого сканирования хранится отдельно и выбирается в поле «Сканирование») и позволяет заблокировать запуск файла по его хэшу.

## Как это работает

| Задача | Реализация |
|---|---|
| Список компьютеров | LDAP-запрос через ADSI (модуль ActiveDirectory не нужен), только включённые компьютеры с Windows; можно ограничить OU |
| Проверка «включён ли компьютер» | перед сбором каждый компьютер проверяется пингом (ICMP, параллельно, ~1 с на все сразу) — выключенные/недоступные по сети сразу считаются сбоем с понятной причиной, вместо того чтобы ждать таймаута WinRM на каждый |
| Сбор процессов | `Invoke-Command` (WinRM) параллельно, на цели `Get-WmiObject Win32_Process`; на целях достаточно PowerShell 2.0 |
| Хэши | MD5, SHA1 и SHA256 считаются на самом компьютере за один проход по файлу; в таблице выбирается нужный алгоритм |
| Пользователь | Владелец каждого процесса (кто его запустил) — метод WMI `GetOwner()`, в виде `ДОМЕН\логин`; системные процессы показываются как `NT AUTHORITY\SYSTEM` и т. п., если владельца определить нельзя — пусто. Один и тот же файл, запущенный разными пользователями, показывается отдельными строками |
| Время запуска | Когда процесс был запущен (`Win32_Process.CreationDate`) — в часовом поясе того компьютера, где он работает; если WMI не отдал время, поле пустое |
| Хранение | JSON-файлы в папке `data\`: каждое сканирование сохраняется отдельным файлом с датой, история не стирается |
| Блокировка | хэш-правило **Software Restriction Policies** уровня «Запрещено» записывается в доменную GPO; можно выбрать сразу несколько строк (Ctrl/Shift+клик) и заблокировать все разом |
| Блокировка по пользователю/группе | то же хэш-правило, но в User Configuration отдельной GPO с Security Filtering, ограниченным выбранным пользователем или группой AD — действует только на него/неё, а не на весь компьютер (см. раздел ниже) |
| Повторная проверка после сканирования | не зависит от GPO: после каждого сканирования (ручного или планового) свежесобранные процессы сверяются с активными блокировками, и совпавшие сразу закрываются — см. раздел «Невод» ниже |

## Требования

На компьютере администратора (откуда запускается приложение):

* Windows PowerShell 5.1, права администратора домена (или делегированные права на WinRM целей и редактирование GPO);
* модуль **GroupPolicy** (RSAT → Group Policy Management) — для блокировки;

Сторонние драйверы и модули для хранения данных не нужны.

На целевых компьютерах:

* включён WinRM / PowerShell Remoting (`Enable-PSRemoting`, либо GPO «Allow remote server management through WinRM»);
* открыт порт 5985/TCP для администратора.

## Запуск

```powershell
powershell -STA -ExecutionPolicy Bypass -File .\ProcessMonitor.ps1
```

1. Вкладка **Компьютеры** → «Загрузить из AD» (при желании укажите DN подразделения), отметьте нужные → «Собрать процессы».
   Кнопка «Сохранить список для плановых сканирований» запоминает отмеченные компьютеры для запуска без окна
   (см. раздел «Плановые сканирования» ниже).
2. Вкладка **Процессы**: выбор сканирования, алгоритма хэша, поиск по имени/хэшу/компьютеру/пути.
   Номер строки в колонке `№` пересчитывается при сортировке и поиске.
3. Выберите строку → **«Заблокировать по хэшу…»**. Можно выделить несколько строк (Ctrl/Shift+клик) и заблокировать
   их все одним нажатием — одно общее подтверждение на весь список, один и тот же файл на разных компьютерах
   считается одной блокировкой, а не несколькими.
4. Вкладка **Блокировки**: имя GPO, привязка (необязательно), область действия («Все пользователи компьютера»
   или «Пользователь/группа AD» — см. раздел ниже), список правил, «Снять блокировку», «Проверить
   срабатывания» (попытки запустить заблокированный файл после блокировки — см. раздел ниже).
5. Вкладка **Журнал**: компьютеры, которые не ответили, и причина.

Данные собираются под учётной записью, от имени которой запущено приложение.

## Плановые сканирования

Чтобы данные обновлялись сами, без открытого окна:

1. На вкладке **Компьютеры** отметьте нужные компьютеры и нажмите **«Сохранить список для плановых сканирований»**
   (список сохраняется отдельно от обычных галочек, в `data\scheduled-computers.json`; кнопка «Загрузить
   сохранённый список» показывает его снова, если нужно свериться или поправить).
2. Добавьте в **Планировщик заданий Windows** (`taskschd.msc`) задание, запускающее:
   ```
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\путь\ProcessMonitor.ps1" -ScheduledScan
   ```
   Окно при этом не открывается; результат — обычное новое сканирование (видно на вкладке «Процессы» при
   следующем запуске окна) и запись в `data\logs\processmonitor.log`.

**Важно про учётную запись задания.** WinRM к ДРУГИМ компьютерам нужна сетевая идентичность с правами на них.
Задание, запущенное как `SYSTEM` (частый вариант по умолчанию), сетевого доступа к другим машинам не имеет и
скорее всего не сможет их опросить. Создавайте задание от настоящей учётной записи (доменной, с правами на
WinRM/WMI целевых компьютеров) с опцией **«Run whether user is logged on or not»** и сохранённым паролем — так,
как обычно настраивают сервисные задания в Планировщике.

`-ScheduledScan` сам новых блокировок не создаёт — решение заблокировать что-либо по-прежнему принимает человек
на вкладке «Процессы»; это сделано намеренно: скрипт по расписанию не должен сам решать, что запрещать в домене.
Но УЖЕ существующие активные блокировки он проверяет и применяет автоматически — после каждого планового
сканирования запущенные экземпляры уже заблокированных файлов сразу закрываются (см. «Невод» ниже). Поэтому
частота плановых сканирований — это ещё и то, насколько быстро такой процесс будет закрыт после повторного
запуска.

**«Постоянное» сканирование активных компьютеров.** Само приложение не содержит бесконечного цикла — это
сознательно оставлено Планировщику заданий: поставьте в задании повторение (вкладка «Триггеры» → «Повторять
задачу каждые: ...», например каждые 5 минут) и `-ScheduledScan` будет запускаться постоянно, снова и снова,
без участия человека. Каждый такой запуск сам проверяет пингом, какие из сохранённого списка компьютеров сейчас
включены (см. таблицу выше) — выключенные просто пропускаются в этот раз (с пометкой в журнале, не как ошибка)
и будут опрошены при следующем запуске, когда включатся. Отдельно настраивать список "активных" компьютеров не
нужно — он определяется заново при каждом запуске.

## Проверка срабатываний блокировки

Кнопка **«Проверить срабатывания»** на вкладке «Блокировки» ищет в журнале событий Windows (`Application`, источник
`SRP`, события Software Restriction Policies с кодами 865/866/867/868/882) попытки запустить файл выбранной
блокировки на всех компьютерах, где он хоть когда-то встречался (не только в последнем сканировании), с момента
блокировки. Результат — число срабатываний и время последнего — сохраняется и видно в колонках «Срабатываний» /
«Последнее срабатывание» даже после перезапуска приложения.

**Эти коды событий и имя источника — по документации Microsoft о Software Restriction Policies, не проверены на
реальном журнале событий.** Если на вашей версии Windows они окажутся другими, проверка просто ничего не найдёт
(покажет «Срабатываний: 0»), а не завершится ошибкой — то есть худший случай при несовпадении: ложное «ничего не
найдено», а не сбой. Проверьте один раз на тестовой машине: заблокируйте что-нибудь безобидное, запустите его
заново на заблокированном компьютере и нажмите «Проверить срабатывания» — если счётчик не увеличился, напишите мне
точный код и источник события из Просмотра событий (`eventvwr.msc`), чтобы поправить код события/условие поиска.

## Журнал работы

Всё, что видно на вкладке «Журнал» (ошибки, не ответившие компьютеры, итоги сбора и блокировок), одновременно дописывается
в файл `data\logs\processmonitor.log` с датой и временем каждой записи. При перезапуске файл не затирается, а в окне
показываются последние 200 строк прошлых запусков. Кнопка «Открыть файл журнала» открывает файл в Блокноте. Когда файл
вырастает больше 5 МБ, он переименовывается в `processmonitor.log.1` (предыдущая копия `.1` заменяется) и начинается новый.
Ошибка записи в журнал (нет прав, файл занят) программу не останавливает.

## Самопроверка

Перед первым боевым запуском выполните на своей машине:

```powershell
powershell -STA -ExecutionPolicy Bypass -File .\ProcessMonitor.ps1 -SelfTest
```

Окно не открывается; скрипт проверяет версию PowerShell, JSON-хранилище (во временной папке), хэширование процессов
(с эталоном `Get-FileHash`), Windows Forms, а также наличие модуля GroupPolicy, доступ к AD и работу WinRM на этом компьютере.
Каждый пункт печатается как `[ OK ]`, `[WARN]` (необязательно: нет RSAT, AD или WinRM) или `[FAIL]`.

## Как работает блокировка

Правило пишется в `Registry.pol` GPO через `Set-GPRegistryValue`:

```
HKLM\Software\Policies\Microsoft\Windows\Safer\CodeIdentifiers\0\Hashes\{GUID}
    ItemData (Binary) — хэш, ItemSize (QWord) — размер файла, HashAlg (DWord), SaferFlags = 0
```

Если в GPO ещё нет базовых параметров SRP, добавляются `DefaultLevel = Unrestricted` (всё, что не запрещено правилом, работает
как раньше), `TransparentEnabled = 1`, `PolicyScope = 0` и стандартный список расширений.

* Если GPO не существует, она создаётся. **Привязывайте её к нужному OU** — поле «Привязать к» на вкладке
  «Блокировки» это выпадающий список: кнопка «Загрузить OU из AD» заполняет его подразделениями домена (первый
  пункт — «(весь домен)», чтобы привязать сразу ко всему домену), можно выбрать пункт или, как раньше, вписать
  либо вставить DN вручную. То же самое можно сделать и в GPMC. **Без привязки (Link) правило не действует вообще
  нигде**, сколько бы раз ни выполнялся `gpupdate`: клиент просто не берёт непривязанную GPO в обработку. Это самая
  частая причина «заблокировал, а процесс всё равно запускается». Приложение проверяет это через отчёт GPO
  (`GenerateReport`) и предупреждает отдельным окном *до* подтверждения блокировки, если у GPO сейчас нет ни одной
  включённой привязки, а поле «Привязать к» пустое; та же причина, если она сработала, попадает в журнал строкой
  «ВНИМАНИЕ: …».
* **Блокировка применяется сразу, без отдельных флажков.** На всех компьютерах, где файл встречался в последнем
  сканировании, сразу после добавления правила приложение само:
  1. обновляет политики (`gpupdate /target:computer /force`) — правило SRP действует немедленно, а не только после
     планового обновления (по умолчанию до 90 минут);
  2. завершает уже запущенные экземпляры файла (`Win32_Process.Terminate()`);
  3. показывает каждому пользователю, у кого файл был запущен, сообщение на экране (`msg.exe`) — по умолчанию
     «Нельзя такое запускать: «‹имя файла›» заблокировано политикой безопасности.» Текст можно посмотреть и
     поменять в коде через `$script:NotifyTemplate`.
  Если компьютер, на котором видели файл, определить не удалось (нет данных сканирования), ничего из этого не
  запускается — политика дойдёт до клиентов при плановом обновлении; пересканируйте и заблокируйте ещё раз.
* Журнал показывает результат по каждому компьютеру: обновились ли политики (`gpupdate`), сколько запущенных
  экземпляров **найдено**, сколько реально **завершено** и скольким пользователям показано уведомление.
  Found = 0 при непустом списке компьютеров значит, что на момент применения процесс уже не был запущен (завершился
  сам или данные сканирования устарели — пересканируйте). Found > Killed значит, что экземпляры найдены, но
  `Terminate()` их не завершил (уведомление в этом случае не отправляется — файл ведь не закрылся); причина
  указывается рядом («нет прав на завершение процесса» — самая частая: учётная запись, под которой запущено
  приложение, должна быть локальным администратором на целевом компьютере). Уведомление отправляется один раз на
  пользователя, даже если у него было открыто несколько копий файла; требует, чтобы на целевом компьютере работала
  служба Remote Desktop Services (обычно работает по умолчанию) — если нет, `Notified` будет меньше `Killed`.
* **Принудительное завершение сеанса — по отдельному вопросу, не автоматически.** Если найдены компьютеры с
  запущенным файлом, после добавления правила приложение отдельно спрашивает: завершить ли принудительно сеанс
  пользователя(ей), у которых процесс был закрыт (`logoff.exe`) — «в целях безопасности и предотвращения
  нарушений». Ответ по умолчанию — «Нет» (как и у всех подтверждений в приложении), потому что это закрывает ВСЕ
  открытые у человека программы на этом компьютере, а не только заблокированный файл, и отключает его от сеанса
  немедленно. Выполняется только для сеансов, где процесс реально завершился (`Terminate()` удался), один раз на
  сеанс — журнал показывает это как `завершено сеансов: N`.
* Блокировать файлы в `X:\Windows\…` запрещено программно: правило на `svchost.exe`, `explorer.exe` и т. п. остановит весь домен.
* По умолчанию (область «Все пользователи компьютера») правило применяется ко всем пользователям компьютера,
  включая администраторов. Администратор может снять блокировку кнопкой «Снять блокировку» (правило удаляется
  из GPO).

## Блокировка по пользователю/группе

На вкладке «Блокировки» в поле «Область» можно выбрать «Пользователь/группа AD» вместо «Все пользователи
компьютера» — тогда правило подействует не на весь компьютер, а только на конкретного человека или участников
группы, независимо от того, на какой машине домена он войдёт. Кнопка «Загрузить пользователей/группы из AD»
заполняет список рядом (поле «Пользователь/группа»); можно выбрать пункт или набрать `sAMAccountName` вручную.

Как это устроено технически:

* Хэш-правило пишется в **User Configuration** той же GPO (`HKCU\...\Safer\CodeIdentifiers\...`, а не
  `HKLM\...`), поэтому действует для пользователя, а не для компьютера.
* Само ограничение «для кого именно» даёт не это, а **Security Filtering** GPO: приложение убирает у GPO право
  «Apply group policy» у `Authenticated Users` (которое `New-GPO` ставит по умолчанию и которое означает «для
  всех») и выдаёт его только выбранному пользователю/группе (`Set-GPPermission`). Без этого шага правило в User
  Configuration подействовало бы на всех, кто попадает под привязку GPO — ровно как обычная блокировка на весь
  компьютер.
* Из этого следует, что **каждому пользователю/группе — своя отдельная GPO**: имя GPO из поля «GPO» используется
  как базовое, и к нему автоматически добавляется суффикс, например «Process Hash Block (SRP) - Пользователь:
  ivanov» или «… - Группа: finance». Это важно: Security Filtering действует на GPO целиком, а не на отдельное
  правило внутри неё — если бы несколько пользователей использовали одну GPO, SRP-правила всех них действовали бы
  на каждого из них.
* Привязка (поле «Привязать к») нужна точно так же, как и для обычной блокировки — без неё GPO всё равно не
  возьмётся в обработку. Привязывать такую GPO удобнее всего к домену целиком: кого именно она коснётся, в любом
  случае решает Security Filtering, а не то, к какому OU она привязана.
* **Немедленное закрытие уже запущенного файла** (сразу после добавления правила) учитывает это ограничение
  только для пользователя: закрывается, с уведомлением и (если выбрано) завершением сеанса, только тот процесс,
  владелец которого совпадает с выбранным пользователем — у других, кто сейчас запустил тот же файл, он не
  трогается. **Для группы такой проверки нет** — закрываются все текущие запущенные экземпляры файла независимо
  от членства в группе (сверить членство можно было бы только отдельным запросом к AD с целевого компьютера, это
  не реализовано и не проверено на реальном домене). Сама блокировка новых запусков при этом всё равно верно
  ограничена только членами группы — это даёт Security Filtering, а не немедленное закрытие. Приложение
  предупреждает об этом отдельной строкой в окне подтверждения при блокировке группы.
* Снятие блокировки (кнопка «Снять блокировку») удаляет правило из нужного раздела (`HKLM` или `HKCU`)
  автоматически — это видно в колонке «Применяется к» на вкладке «Блокировки».
* Это не проверено на реальном домене (как и остальная работа с GPO в этом приложении) — перед использованием на
  живых пользователях опробуйте на тестовой учётной записи/группе и тестовом OU.

## Невод: повторная проверка после сканирования (без GPO)

GPO и SRP зависят от исправной групповой политики на целевом компьютере (а она ломается — например, повреждённая
локальная GPO компьютера может остановить применение ЛЮБЫХ политик, включая доменные, независимо от того,
правильно ли всё настроено на стороне приложения). Чтобы блокировка работала даже при таких проблемах,
приложение **дополнительно**, отдельно от GPO/SRP, после **каждого** сканирования — и ручного (кнопка «Собрать
процессы»), и планового (`-ScheduledScan`, см. «Плановые сканирования» выше) — сверяет свежесобранные процессы
с активными блокировками (вкладка «Блокировки») и, если хэш совпал, сразу закрывает такой процесс и показывает
уведомление — без обращения к `gpupdate`, без зависимости от того, привязана ли GPO, работает ли локальная
групповая политика на этом компьютере и т. п.

Как это соотносится с SRP:

* **Это не замена SRP, а подстраховка.** SRP (когда работает) не даёт процессу запуститься вообще; невод
  реагирует уже ПОСЛЕ того, как процесс запущен — то есть между запуском заблокированного файла и следующим
  сканированием есть окно, в которое он успевает поработать. Насколько короткое это окно — зависит от того, как
  часто вы запускаете плановые сканирования (см. «Плановые сканирования»): чем чаще, тем быстрее сработает невод.
* Правило SRP в GPO по-прежнему создаётся при блокировке, как раньше — на случай, если групповая политика всё же
  заработает (сразу или после починки), она даст более сильную, мгновенную защиту. Невод работает параллельно и
  не требует, чтобы GPO вообще применилась.
* Принудительное завершение сеанса пользователя в невод не входит — это осталось только явным действием при
  самой блокировке (вопрос «Завершение сеанса пользователя»), не автоматическим фоновым.
* В журнале (и в файле `processmonitor.log` при плановых сканированиях) строки невода помечены «После
  сканирования: …».

### Ограничения, о которых нужно знать

* **Не проверено на живом домене.** Код проверен только на синтаксис и отдельные части (хэширование, SQL, разбор заданий);
  интерфейс, WinRM и запись в GPO нужно сначала опробовать на тестовом OU / тестовой машине.
* SRP-механизм хэширует файл по своим правилам. Для **подписанных (Authenticode) исполняемых файлов** хэш SRP может не совпасть
  с хэшем всего файла, который показывает приложение, — тогда правило не сработает. Для неподписанных файлов хэши обычно совпадают.
  Проверьте правило на тестовой машине (запустите файл после `gpupdate`).
* SRP официально предлагает алгоритмы **MD5** и **SHA-256**. SHA1 принимается приложением, но поддержку этого значения на целевых ОС
  проверьте на тесте; по умолчанию выбран MD5.
* Один файл — один хэш: перекомпилированная или изменённая копия имеет другой хэш и правилом не блокируется.
* Размер файла (`ItemSize`) тоже участвует в сопоставлении, поэтому правило привязано к конкретной сборке файла.
* Процессы без доступного пути к файлу (System, Idle) пропускаются; файлы, которые не удалось прочитать, тоже.
* **Коды событий в «Проверить срабатывания» не проверены на реальном журнале Windows** (см. раздел выше) — взяты
  из документации Microsoft, могут потребовать уточнения на практике.

## Структура и хранение данных

Всё приложение — один файл `ProcessMonitor.ps1` (интерфейс, хранилище, сбор, блокировка). Данные лежат в папке `data\`
рядом со скриптом (другая папка — параметр `-DataPath`):

```
data\scans.json               список сканирований: номер, дата, сколько компьютеров ответило, их имена
data\scans\scan-000001.json   процессы одного сканирования (отдельный файл на каждое)
data\blocks.json              журнал блокировок
data\scheduled-computers.json список компьютеров для плановых сканирований (см. "Плановые сканирования")
data\logs\processmonitor.log  журнал работы программы (записи дописываются, не стираются)
```

Файлы — обычный UTF-8 JSON, их можно открыть любым редактором. Запись идёт через временный файл, поэтому обрыв
не портит уже сохранённое. Приложение рассчитано на один запущенный экземпляр. Данные, ранее сохранённые в SQLite
(`processes.db`), не импортируются.

Файл сохранён в UTF-8 **с BOM** — это нужно Windows PowerShell 5.1 для корректного чтения кириллицы.
Если будете править, сохраняйте в той же кодировке (иначе кириллица будет испорчена).
