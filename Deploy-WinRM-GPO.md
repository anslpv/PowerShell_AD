# Автоматическая настройка WinRM через GPO (сценарий запуска компьютера)

Инструкция разворачивает `Setup-WinRM-Target.ps1` на все компьютеры домена (или на выбранное
подразделение) через групповую политику: скрипт выполняется **при каждой загрузке компьютера**, от имени
**SYSTEM** (поэтому не нужны права пользователя — локальные права уже есть), **до входа любого пользователя**
в систему. Если WinRM уже настроен правильно — скрипт просто подтверждает это и ничего не меняет
(безопасно выполнять при каждой загрузке).

Это именно **сценарий запуска компьютера** (Computer Startup Script), а не сценарий входа пользователя —
потому что настройка службы и брандмауэра требует прав администратора, а обычный пользователь домена ими не
обладает. Запуск от SYSTEM при загрузке решает это: к моменту, когда за компьютер садится пользователь,
WinRM уже гарантированно настроен.

## Шаг 1. Скопировать скрипт в SYSVOL

Любой сценарий GPO должен быть доступен всем компьютерам домена по сети — для этого используется папка
`SYSVOL`, которая автоматически реплицируется на все контроллеры домена.

1. На контроллере домена (или с компьютера администратора, у которого есть доступ) откройте:
   ```
   \\<домен>\SysVol\<домен>\scripts\
   ```
   Например: `\\pp.local\SysVol\pp.local\scripts\`
2. Скопируйте туда `Setup-WinRM-Target.ps1` из этого репозитория.
3. Подождите репликации SYSVOL между контроллерами домена (обычно до нескольких минут; если домен с одним
   контроллером — изменение видно сразу).

## Шаг 2. Создать (или использовать существующую) групповую политику

1. Откройте **Group Policy Management** (`gpmc.msc`) на контроллере домена или любом компьютере с
   установленными средствами администрирования AD.
2. Правой кнопкой на подразделении (OU) или на самом домене (в зависимости от того, на какие компьютеры
   должна распространяться настройка — см. шаг 4) → **«Создать GPO в этом домене и связать его...»**.
3. Назовите политику понятно, например: **«Настройка WinRM (Process Monitor)»**.

## Шаг 3. Настроить сценарий запуска

Откройте созданную GPO на редактирование (правой кнопкой → **«Изменить»**) и перейдите в:

```
Конфигурация компьютера → Политики → Конфигурация Windows → Сценарии (запуск)
```

Дальше в зависимости от версии GPMC — два равнозначных варианта:

### Вариант А — есть отдельная вкладка «Сценарии PowerShell» (GPMC на Windows Server 2016 и новее)

1. Откройте вкладку **«Сценарии PowerShell»**.
2. **«Добавить»** → укажите путь к файлу: `\\<домен>\SysVol\<домен>\scripts\Setup-WinRM-Target.ps1`.
3. Параметры скрипта оставьте пустыми — скрипт их не требует.
4. Порядок выполнения (если есть другие сценарии) — не важен, можно оставить по умолчанию.

### Вариант Б — только обычная вкладка «Сценарии (запуск)» (GPMC постарше, вплоть до Server 2008/2012)

Старый узел GPO понимает только `.bat`/`.cmd`/`.vbs` напрямую, поэтому .ps1-файл запускается через
`powershell.exe`:

1. **«Добавить»**.
2. **«Имя сценария»**: `powershell.exe`
3. **«Параметры сценария»**:
   ```
   -NoProfile -ExecutionPolicy Bypass -File "\\<домен>\SysVol\<домен>\scripts\Setup-WinRM-Target.ps1"
   ```
   (замените `<домен>` на реальное имя домена, например `pp.local`).

> Если в домене отдельной политикой ограничено выполнение только подписанных сценариев
> («Включить выполнение сценариев» = «Только подписанные сценарии», `AllSigned`) — `-ExecutionPolicy Bypass`
> в параметрах запуска всё равно работает (это параметр самого вызова `powershell.exe`, а не отдельная
> политика выполнения сценариев уровня системы), но если в домене явно задана GPO
> **«Turn on Script Execution»** со значением `Allow only signed scripts` — её действие шире, и скрипт нужно
> будет подписать сертификатом либо временно исключить эту настройку для целевых компьютеров.

## Шаг 4. Привязать политику к нужным компьютерам

* **Весь домен** — GPO, созданная прямо на уровне домена (правый клик на имени домена в GPMC), автоматически
  действует на все компьютеры во всех подразделениях (если не заблокировано наследование ниже).
* **Отдельное подразделение** — свяжите GPO с конкретным OU (правый клик на OU → **«Связать существующий
  GPO...»**, если GPO уже создана на шаге 2 в другом месте).

Фильтрация безопасности (вкладка **«Область»** GPO) по умолчанию включает **«Authenticated Users»** с правом
«Применить» — этого достаточно, так как учётные записи компьютеров (не только пользователей) тоже входят в
группу Authenticated Users. Менять не нужно, если не используется более тонкая фильтрация по группам
компьютеров.

## Шаг 5. Применить и проверить

* Быстрая проверка без ожидания перезагрузки (на одном тестовом компьютере):
  ```powershell
  gpupdate /force
  gpresult /r /scope computer      # убедиться, что GPO применилась (раздел "Применённые объекты GPO")
  ```
  Сценарии запуска (в отличие от большинства настроек GPO) выполняются **только при следующей
  перезагрузке**, `gpupdate /force` их не запускает повторно — поэтому для реальной проверки перезагрузите
  тестовый компьютер.
* После перезагрузки — на самом компьютере проверьте журнал скрипта:
  ```
  %ProgramData%\ProcessMonitor\winrm-setup.log
  ```
* С компьютера администратора проверьте, что WinRM действительно стал отвечать:
  ```powershell
  Test-WSMan -ComputerName ARM31905
  ```
* Рекомендуется сначала проверить на 1–2 тестовых компьютерах (временно связав GPO с тестовым OU/группой),
  и только потом расширять область действия на весь домен/крупное подразделение.

## Если что-то не заработало

* **Сценарий не выполнился вообще** — проверьте репликацию SYSVOL (шаг 1) и что путь в параметрах сценария
  (шаг 3) написан без ошибок; `gpresult /r /scope computer` на целевом компьютере покажет, применилась ли
  сама GPO.
* **Сценарий выполнился, но в журнале `[ERROR]`** — см. текст ошибки в `winrm-setup.log`: обычно это
  недоступность WinRM как компонента Windows (устаревшая/урезанная установка) — тогда нужно отдельно
  установить/восстановить компонент Windows Remote Management.
* **WinRM всё равно не отвечает с компьютера администратора** — после того как `Test-WSMan -ComputerName
  localhost` на самом целевом компьютере (видно в журнале) проходит успешно, а снаружи — нет: порт
  5985/TCP блокируется не локальным Windows Firewall (его скрипт уже открыл на всех профилях), а
  промежуточным аппаратным брандмауэром/маршрутизатором между подсетями — это нужно открывать отдельно,
  сетевыми средствами, скрипт на это повлиять не может.

## Откат

Чтобы прекратить применение — либо отключите связь GPO с OU/доменом (GPMC → правый клик на связи →
«Связь включена» снять галочку), либо удалите саму GPO. Уже внесённые скриптом изменения (включённый
WinRM, правило брандмауэра) при этом сами не отменяются — это настройки конкретной службы на конкретном
компьютере, а не «временный» эффект GPO.
