# Автоматическая настройка WinRM через GPO (сценарий запуска компьютера)

Инструкция разворачивает `Setup-WinRM-Target.ps1` на все компьютеры домена (или на выбранное
подразделение) через групповую политику: скрипт выполняется **при каждой загрузке компьютера**, от имени
**SYSTEM** (поэтому не нужны права пользователя — локальные права уже есть), **до входа любого пользователя**
в систему. Если WinRM уже настроен правильно — скрипт просто подтверждает это и ничего не меняет
(безопасно выполнять при каждой загрузке).

Это именно **сценарий запуска компьютера** (Computer Startup Script), а не сценарий входа пользователя —
потому что настройка службы и брандмауэра требует прав администратора, а обычный пользователь домена ими не
обладает. Запуск от SYSTEM при загрузке решает это: к моменту, когда за компьютер садится пользователь,
WinRM уже гарантированно настроен.

## Шаг 1. Скопировать скрипт в SYSVOL

Любой сценарий GPO должен быть доступен всем компьютерам домена по сети — для этого используется папка
`SYSVOL`, которая автоматически реплицируется на все контроллеры домена.

1. На контроллере домена (или с компьютера администратора, у которого есть доступ) откройте:
   ```
   \\<домен>\SysVol\<домен>\scripts\
   ```
   Например: `\\pp.local\SysVol\pp.local\scripts\`
2. Скопируйте туда `Setup-WinRM-Target.ps1` из этого репозитория.
3. Подождите репликации SYSVOL между контроллерами домена (обычно до нескольких минут; если домен с одним
   контроллером — изменение видно сразу).

## Шаг 2. Создать (или использовать существующую) групповую политику

1. Откройте **Group Policy Management** (`gpmc.msc`) на контроллере домена или любом компьютере с
   установленными средствами администрирования AD.
2. Правой кнопкой на подразделении (OU) или на самом домене (в зависимости от того, на какие компьютеры
   должна распространяться настройка — см. шаг 4) → **«Создать GPO в этом домене и связать его...»**.
3. Назовите политику понятно, например: **«Настройка WinRM (Process Monitor)»**.

## Шаг 3. Настроить сценарий запуска

Откройте созданную GPO на редактирование (правой кнопкой → **«Изменить»**) и перейдите в:

```
Конфигурация компьютера → Политики → Конфигурация Windows → Сценарии (запуск)
```

Дальше в зависимости от версии GPMC — два равнозначных варианта:

### Вариант А — есть отдельная вкладка «Сценарии PowerShell» (GPMC на Windows Server 2016 и новее)

1. Откройте вкладку **«Сценарии PowerShell»**.
2. **«Добавить»** → укажите путь к файлу: `\\<домен>\SysVol\<домен>\scripts\Setup-WinRM-Target.ps1`.
3. Параметры скрипта оставьте пустыми — скрипт их не требует.
4. Порядок выполнения (если есть другие сценарии) — не важен, можно оставить по умолчанию.

### Вариант Б — только обычная вкладка «Сценарии (запуск)» (GPMC постарше, вплоть до Server 2008/2012)

Старый узел GPO понимает только `.bat`/`.cmd`/`.vbs` напрямую, поэтому .ps1-файл запускается через
`powershell.exe`:

1. **«Добавить»**.
2. **«Имя сценария»**: `powershell.exe`
3. **«Параметры сценария»**:
   ```
   -NoProfile -ExecutionPolicy Bypass -File "\\<домен>\SysVol\<домен>\scripts\Setup-WinRM-Target.ps1"
   ```
   (замените `<домен>` на реальное имя домена, например `pp.local`).

> Если в домене отдельной политикой ограничено выполнение только подписанных сценариев
> («Включить выполнение сценариев» = «Только подписанные сценарии», `AllSigned`) — `-ExecutionPolicy Bypass`
> в параметрах запуска всё равно работает (это параметр самого вызова `powershell.exe`, а не отдельная
> политика выполнения сценариев уровня системы), но если в домене явно задана GPO
> **«Turn on Script Execution»** со значением `Allow only signed scripts` — её действие шире, и скрипт нужно
> будет подписать сертификатом либо временно исключить эту настройку для целевых компьютеров.

## Шаг 4. Привязать политику к нужным компьютерам

* **Весь домен (рекомендуется, если не уверены)** — GPO, созданная прямо на уровне домена (правый клик на
  имени домена в GPMC → «Создать GPO в этом домене и связать его...»), автоматически действует на все
  компьютеры во всех подразделениях И на компьютеры во встроенных контейнерах по умолчанию (`CN=Computers`) —
  см. важное замечание ниже про этот контейнер. Привязка к домену в целом — единственный способ надёжно
  достать компьютеры, которые туда не переносили из контейнера по умолчанию.
* **Отдельное подразделение (OU)** — свяжите GPO с конкретным OU (правый клик на OU → **«Связать существующий
  GPO...»**, если GPO уже создана на шаге 2 в другом месте) — работает ТОЛЬКО если целевые компьютеры реально
  перенесены в это OU (см. ниже).

Фильтрация безопасности (вкладка **«Область»** GPO) по умолчанию включает **«Authenticated Users»** с правом
«Применить» — этого достаточно, так как учётные записи компьютеров (не только пользователей) тоже входят в
группу Authenticated Users. Менять не нужно, если не используется более тонкая фильтрация по группам
компьютеров.

### ⚠️ Самая частая причина, почему GPO "не срабатывает": контейнер `CN=Computers`, а не OU

Групповые политики можно привязывать **только к сайтам, домену в целом и подразделениям (OU)** — но **не к
обычным контейнерам**, включая встроенный контейнер **«Computers»**, куда по умолчанию попадает каждый новый
компьютер при вводе в домен, если администратор не переносил его в какое-то OU вручную. Если целевой
компьютер сидит именно в этом контейнере, то GPO, привязанная к ЛЮБОМУ подразделению (OU), до него **никогда
не дойдёт** — он просто не входит в область действия ни одного из них, какую бы связь вы ни создавали. При
этом в `gpmc.msc` всё выглядит нормально — ошибки никакой не будет, GPO просто не появится в списке
применённых на этом компьютере.

**Проверка** — узнать, где РЕАЛЬНО находится конкретный компьютер (на нём самом, от обычного пользователя,
права администратора не нужны):

```powershell
([ADSISearcher]"(&(objectCategory=computer)(name=$env:COMPUTERNAME))").FindOne().Properties.distinguishedname
```

Смотрите на результат:
* `CN=ИМЯ,CN=Computers,DC=...` — это тот самый контейнер по умолчанию. Привязка к любому OU работать не
  будет; нужно либо перенести компьютер в OU (`dsa.msc` → правый клик на компьютере → «Переместить...»),
  либо привязать GPO к домену целиком (см. выше) — тогда перенос не требуется вообще.
* `CN=ИМЯ,OU=...,DC=...` — компьютер уже в подразделении; GPO, привязанная к этому OU (или к одному из
  родительских OU, если не стоит блокировка наследования), должна работать.

Если нужно проверить сразу много компьютеров (например, перед тем как привязывать GPO к OU, а не к домену) —
этот фрагмент выводит имена всех компьютеров домена, которые до сих пор сидят в контейнере `Computers`,
прямо из-под учётной записи обычного пользователя домена (без модуля ActiveDirectory, обычный ADSI-поиск):

```powershell
$searcher = New-Object System.DirectoryServices.DirectorySearcher
$searcher.Filter = '(objectCategory=computer)'
$searcher.PageSize = 1000
[void]$searcher.PropertiesToLoad.Add('distinguishedname')
@($searcher.FindAll() | Where-Object { [string]$_.Properties['distinguishedname'][0] -match ',CN=Computers,DC=' } |
    ForEach-Object { [string]$_.Properties['distinguishedname'][0] })
```

## Шаг 5. Применить и проверить

Полный путь проверки — по порядку, на целевом компьютере:

```powershell
# 1) GPO реально дошла до компьютера? (можно проверить СРАЗУ, без перезагрузки - gpupdate обновляет
#    список применённых политик немедленно, даже если сам сценарий запуска выполнится только при загрузке)
gpupdate /force
gpresult /r /scope computer
# Ищите имя вашей GPO в разделе "Применённые объекты групповой политики". Если её там НЕТ -
# смотрите раздел про контейнер CN=Computers выше - это самая частая причина.

# 2) Перезагрузить компьютер - сценарии запуска выполняются ТОЛЬКО при загрузке,
#    gpupdate /force их повторно не запускает.
Restart-Computer

# 3) После перезагрузки, на этом же компьютере - журнал самого сценария:
Get-Content "$env:ProgramData\ProcessMonitor\winrm-setup.log" -Tail 30
# Ищите "[ OK ]" на каждом шаге; "[ERROR]" - см. раздел "Если что-то не заработало" ниже.
```

С компьютера администратора (где запущен Process Monitor) — убедиться, что WinRM реально стал отвечать
СНАРУЖИ, а не только локально на самом компьютере:

```powershell
Test-WSMan -ComputerName ARM31905
```

Рекомендуется сначала проверить на 1–2 тестовых компьютерах (временно связав GPO с тестовым OU/группой, или
прямо с одним тестовым компьютером через фильтрацию безопасности), и только потом расширять область действия
на весь домен/крупное подразделение.

## Если что-то не заработало

* **Сценарий не выполнился вообще** — проверьте репликацию SYSVOL (шаг 1) и что путь в параметрах сценария
  (шаг 3) написан без ошибок; `gpresult /r /scope computer` на целевом компьютере покажет, применилась ли
  сама GPO.
* **Сценарий выполнился, но в журнале `[ERROR]`** — см. текст ошибки в `winrm-setup.log`: обычно это
  недоступность WinRM как компонента Windows (устаревшая/урезанная установка) — тогда нужно отдельно
  установить/восстановить компонент Windows Remote Management.
* **WinRM всё равно не отвечает с компьютера администратора** — после того как `Test-WSMan -ComputerName
  localhost` на самом целевом компьютере (видно в журнале) проходит успешно, а снаружи — нет: порт
  5985/TCP блокируется не локальным Windows Firewall (его скрипт уже открыл на всех профилях), а
  промежуточным аппаратным брандмауэром/маршрутизатором между подсетями — это нужно открывать отдельно,
  сетевыми средствами, скрипт на это повлиять не может.

## Приложение: альтернатива — задание по входу пользователя (если сценарий запуска компьютера не подходит)

Основной способ в этой инструкции — сценарий запуска КОМПЬЮТЕРА (`Конфигурация компьютера → Сценарии
(запуск)`) — не требует выбора учётной записи вообще (всегда выполняется от SYSTEM) и должен работать почти
всегда, если GPO реально привязана к компьютеру (см. шаг 4). Но если по какой-то причине настройка должна
триггериться по ВХОДУ конкретного пользователя (а не по загрузке компьютера) — например, компьютеры
организованы неудобно для привязки по OU, а пользователи — удобно, — используется:

```
Конфигурация пользователя → Настройки (Preferences) → Параметры панели управления → Назначенные задания
→ Новый → Запланированное задание (как минимум Windows 7)
```

* Вкладка **«Общие»**: «Пользователь или группа» → **«Изменить пользователя или группу...»** → ввести
  `NT AUTHORITY\SYSTEM` (или SID `S-1-5-18`) → **обязательно** отметить «Выполнять с наивысшими правами».
* Вкладка **«Триггеры»**: Новый → «При входе в систему» → «Любой пользователь».
* Вкладка **«Действия»**: Новый → «Запуск программы» → Программа: `powershell.exe`, аргументы:
  `-NoProfile -ExecutionPolicy Bypass -File "\\<домен>\SysVol\<домен>\scripts\Setup-WinRM-Target.ps1"`.
* GPO привязывается к OU/группе, где состоит ПОЛЬЗОВАТЕЛЬ (не компьютер) — применяется при его входе на
  любой компьютер, независимо от того, в каком OU/контейнере сидит сам компьютер.

**Известная проблема этого способа**: если редактировать GPO **прямо на контроллере домена**, диалог
«Изменить пользователя или группу» не находит `SYSTEM` ни по имени, ни по SID (`«Не удаётся найти "SYSTEM"»`)
— на контроллере домена нет локальной базы учётных записей (SAM), а этот конкретный диалог ищет через неё.
**Решение**: открыть и отредактировать эту же GPO с обычного компьютера/сервера-члена домена (не
контроллера) с установленным RSAT (`Add-WindowsCapability -Online -Name
Rsat.GroupPolicy.Management.Tools~~~~0.0.1.0`) — сама GPO хранится в домене, а не на конкретной машине, так
что результат будет одинаковым независимо от того, с какого компьютера её редактировали; на обычном
компьютере в кнопке «Размещение...» появится сам этот компьютер как источник локальных учётных записей, и
`SYSTEM` разрешится нормально.

## Откат

Чтобы прекратить применение — либо отключите связь GPO с OU/доменом (GPMC → правый клик на связи →
«Связь включена» снять галочку), либо удалите саму GPO. Уже внесённые скриптом изменения (включённый
WinRM, правило брандмауэра) при этом сами не отменяются — это настройки конкретной службы на конкретном
компьютере, а не «временный» эффект GPO.
